# ExtensionInstaller v3.0.2 functional audit

## Purpose

This document decomposes the retained v3.0.2 baseline before migration to release-driven installation.

## Functional blocks

| Area | v3.0.2 responsibility | Migration disposition |
| --- | --- | --- |
| Bootstrap | CMD extracts embedded PowerShell to a temporary file and executes it | Keep |
| Logging/state | Session log, `settings.json`, per-extension `state.json` | Keep, adapt source metadata |
| Local discovery | Scan a user-selected root for extension folders containing ZIP files | Replace as primary discovery path |
| ZIP/manifest parsing | Read extension name/version/manifest key from local ZIP | Remove from normal install path |
| RSA key management | Find/create/migrate `RSA_PRIVATE_KEY.txt` and legacy binary key | Remove from target installer |
| Manifest mutation | Inject public key into extracted `manifest.json` | Remove from target installer |
| Package preparation | Extract ZIP, copy tree, rebuild payload ZIP | Remove from target installer |
| CRX3 generation | Embedded C# signs ZIP with local private RSA key | Remove from target installer |
| Identity | Derive Extension ID from local private/public key | Replace with pinned catalog ID + CRX inspection |
| Browser registration | Write CRX path/version under Yandex extension registry key | Keep |
| Rollback | Restore previous registry values / previous CRX when install fails | Keep and strengthen |
| Uninstall | Remove owned Yandex registration and local CRX/state | Keep |
| Browser assistance | Activate Yandex Browser and guide user to `browser://tune/` | Keep |
| GUI | Folder picker, extension selector, install/update/delete/log actions | Rework for catalog/releases |

## RSA coupling in v3.0.2

The private key is not an isolated optional feature. It currently participates in all of the following:

1. selection identity;
2. first-install identity creation;
3. legacy-key migration;
4. manifest public-key injection;
5. payload ZIP regeneration;
6. CRX3 generation/signing;
7. final Extension ID verification.

Therefore deleting `RSA_PRIVATE_KEY.txt` support before introducing a trusted release input would break installation rather than migrate it.

## New trust/input boundary

Normal installation must instead receive:

1. a pinned catalog entry owned by ExtensionInstaller;
2. a GitHub Release descriptor;
3. an already signed CRX asset;
4. a pinned expected Extension ID;
5. a declared SHA-256 for the CRX;
6. local CRX3 inspection before browser registration.

The extension repository becomes responsible for source packaging and signing. ExtensionInstaller becomes responsible for discovery, download, validation, registration, update, rollback and diagnostics.

## Legacy removal gate

The following v3.0.2 functions become removable only after the release path has passed an end-to-end Yandex Browser update test:

- `Get-ExtensionFolders`
- `Get-LatestZip`
- `Read-ManifestFromZip`
- `Expand-ZipSafely`
- `Find-ExtractedExtensionRoot`
- `Read-ManifestFromFolder`
- `Set-ManifestPublicKey`
- `Copy-ExtensionTree`
- `New-ExtensionZip`
- `Get-KeyFilePath`
- `Ensure-FolderPrivateKey`
- signing portions of `Initialize-CrxGenerator`

Browser registration, state ownership checks and rollback must not be discarded with the signing code.
